# Пошаговая разработка интерфейса

Задача заказчика: «чтобы разработка была чётко пошаговая: база, дизайн, шрифт, расположение, отдельно каждый блок рисуется». Порядок ниже НЕ переставлять и шаги не склеивать. У каждого шага есть **выход** (файл или скриншот) и **ворота** (что проверить, прежде чем идти дальше). Не прошли ворота — шаг не закончен.

Не-разработчику показываем результат картинками, а не кодом. Пишем по-русски.

## Папка работы

```
<проект>/redesign-<экран>-<дата>/
  00-brief.md          цель, данные, главный вопрос экрана
  01-refs/             скриншоты референсов + refs.md (какую МЕХАНИКУ берём из каждого)
  02-tokens.css        база: цвета, поверхности, линии, радиусы, отступы
  03-type.css          шрифт: семья, шкала, веса, цифры
  04-layout.md         схема расположения блоков (ASCII) + сетка
  blocks/NN-имя.html   стенд КАЖДОГО блока отдельно (подключает 02+03, свои демо-данные)
  shots/               скриншоты по шагам (1440 и 390)
  screen.html          сборка экрана из блоков
  build.py             собирает blocks → screen.html (блоки не копировать руками)
```

## Шаг 0. Бриф
- Что за экран, кто его открывает, **какой один вопрос он отвечает** (например: «как идут продажи и где проблема?»).
- **Какие данные реально приходят** — прочитать код/API, выписать поля. Не рисовать то, чего нет в данных (или пометить «нужен новый расчёт» и спросить).
- Что оставить обязательно (функции, цели Метрики, кнопки), что запрещено (договорённости с заказчиком, исключения в чек-листе слопа).
- **Выход:** 00-brief.md. **Ворота:** список полей данных сверен с кодом.

## Шаг 1. Референсы
- Сначала своя Библиотека вкуса (скил biblioteka-vkusa) — семья стиля проекта. Потом 3–5 внешних РЕАЛЬНЫХ продуктов (для кабинетов: Plausible, Umami, Vercel, Stripe, Grafana; галереи saasui.design, Mobbin). Снять скриншоты себе (playwright, color_scheme как у проекта) и посмотреть глазами.
- Из каждого выписать **механику** (что делает: «клик по цифре переключает график», «полоска-доля за строкой списка»), а не внешний вид. Образец ≠ копия: функции берём, оформление своё.
- Назвать механики заказчику сразу и списком.
- **Выход:** 01-refs/ + refs.md. **Ворота:** у каждой механики указан источник; ни одна не из списка 40 клише.

## Шаг 2. База (токены)
- Фон, 2–3 поверхности, линии (2 толщины/яркости), текст 3 уровня, **один** акцент, статусы (рост/падение/внимание), радиусы, шкала отступов 4/8 (4 8 12 16 24 32 48).
- Цвета берём от бренда/лендинга проекта, не «по умолчанию». Без фиолетово-синего, без градиентов, тени только нейтральные.
- Контраст текста ≥ 4.5:1 (второстепенный ≥ 3:1 только для крупного). Проверить числом.
- **Выход:** 02-tokens.css + стенд-палитра (shots/02-tokens.png). **Ворота:** контраст посчитан; акцент один.

## Шаг 3. Шрифт
- Семья (как у бренда), шкала из 6–7 ступеней (например 12/13/15/18/24/32/44), веса (не больше трёх), межстрочный, `font-variant-numeric: tabular-nums` для всех чисел.
- Капс — только мелкие подписи и с разрядкой ≤ 0.04em (№36). Двухцветный заголовок (вторая часть серым) — приём монохрома, можно.
- **Выход:** 03-type.css + стенд «образец текста и цифр» (shots/03-type.png). **Ворота:** крупное число и мелкая подпись читаются на 390 px.

## Шаг 4. Расположение
- Сначала схема ASCII в 04-layout.md: блоки сверху вниз **по важности** (главная цифра/график выше, справочное ниже), ширины колонок, что сворачивается на телефоне.
- Сетка: максимальная ширина, колонки, отступы между блоками из шкалы.
- **2–4 варианта раскладки на выбор, а не один** (заказчик: «ты один вариант сделал?»). Варианты должны различаться подачей, а не цветом: например «полоса цифр + график», «график на весь экран», «сначала вывод словами», «по образцу заказчика». Блоки общие, вариант = другой порядок и сетка рядов (в build.py словарь VARIANTS → screen-A/B/C/D.html) + сравнительная картинка рядом (shots/11-variants-compare.png).
- Если заказчик прислал свой образец — один вариант всегда по его расположению (цвета/свечения образца не брать, если они в чек-листе слопа).
- **Выход:** 04-layout.md. **Ворота:** у каждого блока есть ответ «зачем он здесь».

## Шаг 5. Каждый блок отдельно
Для КАЖДОГО блока свой стенд `blocks/NN-имя.html`:
1. Подключает только 02-tokens.css и 03-type.css (никаких своих цветов мимо токенов).
   **Все классы с префиксом проекта** (например `rp-`): блоки потом встают в чужую страницу, а там свои `.panel`, `.btn`, `.tp`, `.hd` — без префикса стили смешиваются (так уже разваливались шапка и топ). Модификаторы тоже с префиксом (`rp-on`, `rp-hi`). Общее для блоков (демо-данные, форматтеры, списки метрик) — в `_common.js`, а не внутри одного блока: стенд блока грузит только себя.
   Текст из данных (названия товаров и т.п.) вставлять через экранирование (`esc()`), не сырым innerHTML.
2. Реалистичные демо-данные из шага 0 (те же поля, что в API).
3. Состояния: обычное · пустое (нет данных) · загрузка · ошибка · длинные названия · отрицательные/нулевые числа.
4. Скриншот 1440 и 390 → посмотреть глазами → поправить → только потом следующий блок.
- Порядок блоков — как в схеме, сверху вниз.
- **Выход:** blocks/*.html + shots/05-NN-*.png. **Ворота:** все состояния сняты, без горизонтального скролла, JS без ошибок в консоли.

## Шаг 6. Сборка
- build.py склеивает блоки в screen.html (один источник правды — блоки). Ячейкам сетки — `min-width:0`, иначе широкий блок (полоса с прокруткой) распирает страницу на телефоне.
- **Показ в контексте:** подставить собранный экран в живую страницу (например, превью кабинета) через playwright — заготовка `incab.py`: открыть страницу, заменить содержимое основной области, добавить стили и скрипт. Только так видно, что ломают чужие стили и как блок стоит рядом с сайдбаром.
- Проверить ритм: одинаковые отступы между блоками, выравнивание по общим линиям, нет двух соседних «громких» блоков.
- **Выход:** screen.html + shots/06-screen-1440.png. **Ворота:** экран отвечает на вопрос из брифа за 5 секунд взгляда.

## Шаг 7. Поведение
- Наведение (смена цвета/рамки, без подъёма и свечения), клики/переключатели, подсказки на графике, загрузка.
- Анимации держать короткими; без них экран должен читаться полностью.
- **Ворота:** всё кликабельное выглядит кликабельным; ничего не прыгает при загрузке данных.

## Шаг 8. Адаптив
- 1440 · 1024 · 390. Без горизонтальной прокрутки страницы (широкие таблицы — в своём контейнере со скроллом).
- **Выход:** shots/08-*.png.

## Шаг 9. Музей AI-слопа
- Пройти все 40 пунктов: чек-лист «Музей AI-слопа» (40 клише, https://ai-slop.matvei-vibecoder.com), по скриншотам и коду. Эмодзи вместо иконок — нет (только линейные SVG одного набора). Тексты: без длинных тире через предложение, без «Начать бесплатно».
- Отчёт одной строкой: «Музей AI-слопа: чисто» или «нашёл и убрал: №…».

## Шаг 10. Показ заказчику
- Скриншоты в чат (десктоп + телефон), коротко: что поменялось и зачем (механики со ссылкой на референс).
- **Не внедрять в боевой** без «да/заливай». Правки → возврат к нужному шагу (цвет → шаг 2, расположение → шаг 4, один блок → шаг 5 только этот блок).

## Шаг 11. Внедрение
- Бэкап боевого файла (локально и на сервере) с датой.
- Правка скриптом (повторяемо от бэкапа), не руками по месту.
- Проверки: синтаксис (py_compile, `node --check` каждого script-блока), превью-инстанс рядом с боевым, клик по всем разделам — 0 ошибок консоли, 0 вечных заглушек.
- Деплой → проверка живого (коды ответов, скриншот) → откат одной командой, если что.

## Шаг 12. Память
- Записать в заметки проекта: что решили, пути, бэкапы, грабли.

## Грабли, которые уже стреляли
- `font:500 13px/1 inherit` — НЕВАЛИДНО (семейство не может быть inherit в сокращении), браузер выкидывает всё правило. Писать `font-weight/size/line-height` по отдельности + `font-family:inherit`.
- Правило «всем детям `>*` position:relative» перебивает у фоновой полоски `position:absolute` (одинаковая специфичность, побеждает последнее) → полоска становится колонкой сетки. Писать `>*:not(.rp-bar)`.
- Имена классов блоков не должны совпадать с классами сборщика экрана (`rp-row`, `rp-screen`) — так уже разваливались строки списка.
- Скрытый блок (пустой div) в ряду сетки даёт двойной отступ → `.rp-row:has(>div:empty:only-child){display:none}`.
- Модули кабинета разбираем ПО ОЧЕРЕДИ по левому меню, каждый по этому скилу, а заливаем ОДИН РАЗ в конце. Папки `redesign-<модуль>-<дата>/`, инструменты (build/shoot/incab) копировать из первого модуля; incab кликает пункт меню модуля перед подстановкой.
- Переименование классов регэкспом путает составные селекторы (`.rp-cn.a` в стилях против `rp-a` в разметке) — префиксовать с самого начала, а не потом. И `open(p,"w")` с чтением того же файла в одном выражении обнуляет файл.
- График на `preserveAspectRatio="none"` растягивает подписи на телефоне — рисовать SVG под реальную ширину контейнера и перерисовывать при смене ширины. Деления оси «круглые» (50/100/150), верх шкалы — ближайший к максимуму.
- Перекрасить старый экран ≠ перестроить: заказчик видит «то же, что хаб». Если просят перестройку — идти с шага 1, а не менять цвета.
- Скелетоны без запасного пути: при 401/нет ключа экран висел пустым. В шаге 5 состояние «нет данных» обязательно.
- Светлый текст на белой кнопке после автозамены цветов — проверять каждую кнопку на скриншоте.
- `pkill -f 'port 8011'` в той же ssh-команде убивает саму ssh-сессию — гасить превью-сервер по pid.
